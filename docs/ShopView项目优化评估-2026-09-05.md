# ShopView 项目优化评估

日期：2026-09-05。检查基于本地 VERSION 1.0.70 的当前工作区，包含未提交代码。

## 结论与检查范围

系统已形成销售、收益、柜位、合同、租赁应收、供应商付款、活动会员分析和手机工作台的业务框架。下一阶段建议优先补齐访问安全、数据可信、手机刷新、发布保障，再围绕现有模块形成“发现问题—分配责任—处理—复核”的管理闭环。

本次进行了项目结构和关键模式扫描，重点阅读前后端入口、认证与权限、数据库配置、销售与收益查询、财务日期、手机页面、部署文件、测试和维护文档。并非逐行审计所有文件，也未对生产环境进行登录、压测、数据对账或漏洞利用。运行的后端检查使用模拟依赖，不读取生产业务数据。未修改业务代码或部署配置。

历史问题记录仅用于选择检查重点；以下现状判断以本次代码及命令结果为依据。

## 一、优先处理的具体问题

### 1. P1：部分查询接口缺少后端身份校验

- 租户列表、搜索、详情仅依赖数据库会话，未要求登录。返回模型包含法人、联系人、电话、邮箱、地址等字段。
- 主应用挂载这些路由时没有全局身份依赖；前端登录页不能阻止直接调用接口。
- 使用真实租户路由、模拟数据库、无 Cookie 的本地 ASGI 请求，`GET /api/tenants/` 返回 HTTP 200。未读取真实租户资料。
- 门店读取、旧仪表盘统计和部分地图读取接口也值得纳入统一排查。

建议：默认所有业务接口要求登录，只有登录回调、必要静态资源和最小健康探针明确放行；再按功能权限、门店/部门范围控制查询。下拉选项接口可以保留最低必要字段，但应与完整业务档案接口分开。

验收：匿名请求返回 401；跨门店账号不能读到其他门店档案；详情、搜索和导出适用同一数据范围。

依据：[租户路由](../python_app/routers/tenants.py#L19)、[租户返回字段](../python_app/schemas/schemas.py#L152)、[路由挂载](../python_app/main.py#L96)。

### 2. P1：通用上传接口缺少身份、类型和大小控制

`/api/objects/upload` 和实际 PUT 上传处理没有登录依赖；处理函数一次性读取整个文件，写入公开挂载的 `/uploads`。代码未校验允许的扩展名、实际文件类型、单文件大小，也未检查目标文件是否已存在。

建议：绑定上传权限和用途；由服务端产生并校验文件标识；按实际业务限制类型与大小，分块写入；禁止普通用户把可执行网页内容上传到应用同源；敏感附件通过鉴权下载接口提供。公开底图与私有附件分开管理。

验收：匿名上传被拒绝；超限文件明确返回 413；不允许的内容无法上传或在应用同源执行；私有附件不能凭地址匿名下载。

依据：[上传处理](../python_app/main.py#L455)、[公开文件挂载](../python_app/main.py#L361)。实施可参考 [OWASP 文件上传建议](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

### 3. P1：凭据管理和生产启动校验需要加固

- 受 Git 跟踪的 Linux Compose 文件含明文企业微信服务密钥；`env.app`、`env.app-only.linux` 也属于跟踪文件。报告不复制任何密钥值。
- 认证代码允许回退到固定开发签名密钥和弱默认管理员密码。
- Compose 中的 `SECRET_KEY`、`JWT_SECRET_KEY` 与认证实际读取的 `AUTH_SECRET_KEY` 名称不同；环境文件可能提供正确值，但目前未见认证模块拒绝默认值的启动检查。
- Compose 默认以 root 覆盖镜像中的非 root 用户；生产入口配置还需要结合实际 HTTPS 终止位置核实 Cookie 安全属性。

建议：将已进入代码的服务密钥纳入轮换；通过部署环境或密钥管理注入；生产启动时缺失/默认认证密钥直接失败。确认新凭据工作后再废止旧凭据，避免中断企业微信登录。生产运行使用受限用户并配置上传目录权限。

验收：代码和交付包模板不含有效密钥；缺少生产密钥不能启动；首次管理员凭据有明确设置流程；企业微信登录与 HTTPS Cookie 回归通过。

依据：[认证默认配置](../python_app/routers/auth.py#L43)、[Linux 部署配置](../docker-compose.app-only.linux.yml#L11)。本次没有验证任何凭据是否仍有效，也没有轮换凭据。

### 4. P1：手机销售同一筛选再次查询，可能继续展示旧数据

- 全局查询缓存设置为 `staleTime: Infinity`，并关闭窗口聚焦刷新。
- 手机普通销售汇总继承该策略；“本财务月”附加查询单独使用 60 秒有效期并允许聚焦刷新。
- `applyDates()` 更新筛选状态和日志，但没有在日期不变时主动刷新查询。

因此，用户留在同一天再次点“查询”，普通销售可能仍使用旧缓存，而财务月金额已经更新。刚修复的“截至当天”日期正确，并不意味着当天数据会持续刷新。

建议：同筛选点击查询也执行刷新；手机页面提供统一刷新入口、最后成功获取时间和数据同步截止时间；同一屏的销售、毛利、财务月指标使用协调的刷新策略。只对实时页使用短缓存，历史已关账报表仍可保留较长缓存。

验收：相同日期重复查询确实重新请求；从其他页面返回和跨午夜时行为明确；加载失败保留旧数据时标明“上次成功数据”，不能显示为零。

依据：[全局缓存](../client/src/lib/queryClient.ts#L44)、[月累计查询](../client/src/pages/mobile-sales-dashboard.tsx#L470)、[普通汇总](../client/src/pages/mobile-sales-dashboard.tsx#L516)、[查询动作](../client/src/pages/mobile-sales-dashboard.tsx#L832)。

### 5. P1：健康检查可能把数据库故障判为服务正常

`/api/health` 在数据库异常时返回 `degraded/unhealthy` 字典，但没有设置失败 HTTP 状态。Docker 使用 `curl --fail`，因此 HTTP 200 会被判定为检查成功。另外，`/api/test-db` 和 `/api/debug/static` 没有身份依赖，会暴露数据库版本、样例门店或目录信息。

建议：拆分进程存活检查与业务就绪检查；依赖数据库失败时就绪接口返回 503；详细诊断只开放给管理员；记录请求标识、耗时、接口和错误类别，建立可查询的慢请求记录。

验收：在隔离环境模拟数据库断连，探针准确报错并触发监控通知；恢复后自动转为就绪。容器 unhealthy 本身不等同于已经配置了自动重启或通知。

依据：[健康检查](../python_app/main.py#L377)、[数据库诊断](../python_app/main.py#L412)、[容器探针](../docker-compose.app-only.linux.yml)。

### 6. P2：财务日期和同比应有统一定义，但保留业务差异

当前确实存在多套规则：

- `financialMonth.ts`：第一期从 1 月 1 日开始，最后一期到 12 月 31 日。
- `daily-followup-report.ts`：1 月期从上年 12 月 29 日开始，12 月 29 日进入下一年 1 月期。
- 主页同比按财务月经过天数对齐；手机月累计按去年同日截止。

这些差异可能来自不同报表的正式要求，不能直接定性为错误，更不能全部强制改成一套日期。

建议：建立具名业务口径，例如“经营跟进财务月”“财务关账年度”“实时月累计”“同日同比”；接口和导出附带口径标识、期间、是否含当天、金额含税状态、租赁/后台剔除项及数据范围。把边界规则集中测试，减少页面各自实现。

验收：9 月 5 日、29 日、跨年、闰年同日都有业务认可的本期/同期示例；两张报表数字不同时，用户能看到差异来自哪里。

依据：[年度财务窗口](../client/src/lib/financialMonth.ts#L9)、[经营跟进窗口](../client/src/lib/daily-followup-report.ts#L79)、[手机同比](../client/src/lib/mobile-sales-financial-month.ts#L12)。

### 7. P2：手机首屏加载应按模块拆分

`App.tsx` 同时静态引入手机页面和桌面主页；桌面主页又静态引入大量报表、地图和管理页面。手机用户也会承担这些模块的加载依赖。当前代码适合先做路由/模块按需加载，再测实际弱网首屏收益。

建议：登录、手机工作台、桌面、地图、复杂报表分块；Excel/PPT 等重依赖按点击时加载。保留清晰加载提示和错误重试，避免切换时白屏。

验收：用相同手机、相同网络测首次加载资源量和可操作时间，记录优化前后结果；没有本次测量依据，不预先承诺降低百分比。

依据：[应用入口](../client/src/App.tsx#L9)、[桌面页面依赖](../client/src/pages/main-dashboard.tsx#L6)。技术机制参见 [React lazy](https://react.dev/reference/react/lazy)。

### 8. P2：长报表需要数据汇总与任务管理

已有连接池预算、销售同步路由线程处理、跨月查询放宽至 90 秒等措施，并有对应测试，这是应保留的基础。但仅增加等待时间不能证明多人使用时仍能满足响应要求。

建议：先记录高频接口、耗时分位数、扫描行数、数据量及并发，再决定优化顺序。日/门店/部门/柜组汇总适合建立可重算的增量汇总；跨年和大导出可转为后台任务，提供进度、取消、完成下载及到期清理。缓存和导出必须带权限范围，且在下载时复核权限。

验收：覆盖日常同时查询、关账集中使用、导出与在线查询并行；校验合计与明细一致、退货/补录能更新汇总。响应目标先作为验收目标讨论，不作为现状描述。

依据：[连接池预算](../python_app/models/database.py#L31)、[销售长查询](../python_app/routers/sales.py#L146)、[并发测试](../tests/test_sales_mobile_endpoint_concurrency.py)。本次未做生产 SQL 执行计划或压测。

### 9. P2：发布、测试和恢复流程需要统一

- 客户端 TypeScript 检查通过，根目录 `npm run check` 则有 6 个 TS2802 错误，根目录与客户端编译配置不一致。
- Linux 镜像使用 `build:no-check`；`npm ci` 失败会回退到 `npm install`，使依赖一致性保障减弱；还关闭了 npm TLS 证书验证。
- 构建镜像使用 Node 18，官方已列为停止支持版本，应升级到受支持的 LTS 并验证依赖兼容性。
- 当前未发现 `.github` CI 目录或统一可执行验收入口；这不排除仓库外已有流水线。
- 备份文档有手工数据库与上传文件备份命令，但本次未找到定时备份、保留策略及恢复演练的证据。

建议：统一部署前检查命令并接入流水线；锁定依赖和构建来源；恢复证书验证；每个发布包带版本、提交或工作区清单、迁移清单、校验和、验证结果及回退步骤。备份覆盖数据库、上传文件和必要配置，在隔离环境定期恢复演练。

验收：关键测试或类型检查失败阻止发布；给定版本能追溯内容；恢复到指定备份后能够登录、查看附件并核对关键业务记录。业务方明确可容忍的数据损失时间与恢复时间。

依据：[Docker 构建](../Dockerfile.linux#L5)、[根编译配置](../tsconfig.json)、[客户端配置](../client/tsconfig.json)、[备份文档](./deployment/DEPLOYMENT-GUIDE.md)。生命周期参考 [Node 官方 EOL 信息](https://nodejs.org/en/about/eol)。

### 10. P2/P3：逐步拆分大文件，清理演示与旧入口

活动分析路由约 7451 行、收益路由约 5601 行、销售路由约 4333 行；系统配置页面约 2918 行。这会增加改动相互影响和审查成本。README 仍主要描述柜位系统，数据库创建说明也未完整反映当前 Alembic 流程。

建议：随业务修改逐步将查询、计算、权限过滤、导出和页面组件分离，优先处理最常修改的模块；保留统一入口但减少重复请求封装。核实旧仪表盘、样例品牌等入口是否使用后，再删除或隔离。更新实际启动端口、迁移、测试和发布文档。

不建议现在整体重写或仅为拆分而引入微服务。

## 二、商场业务上最值得增加的能力

以下是基于现有模块提出的产品方向，不表示仓库中完全没有相应基础能力。

| 优先顺序 | 建议 | 复用基础 | 最小可用范围与价值 |
| --- | --- | --- | --- |
| 1 | 按岗位的“今日待办” | 手机工作台、C券跟进、租赁应收、供应商付款 | 先汇总合同临期、应收逾期、付款待确认三类事项；每项有负责人、到期日、处理记录及关闭依据。让品类主管打开系统就知道要处理什么。 |
| 2 | 数据可信状态 | 已有同步、报表日期与月结快照 | 显示统计期间、同步截止、同步失败、缺失柜组、未归属部门、未匹配合同；区分“零发生”“没有权限”“尚未同步”“请求失败”。 |
| 3 | 品牌经营档案 | 合同、销售、收益、会员、柜位 | 按品牌/柜组集中展示销售、毛利、收费、贡献、面积、合同到期、应收和会员结构；允许钻回原报表与单据，支持续约和调整讨论。 |
| 4 | 收益月结复核工作台 | 已有不可变快照、调整明细和校验 | 将现有月结导入能力形成可审核流程：差异明细、原因分类、证据附件、复核人、版本与导出；补录不应悄悄改变已确认月份。 |
| 5 | 经营异常跟进 | 销售同比、收益地图、品类管理 | 从持续下滑、负毛利、异常退货、低贡献、空置开始；阈值按门店/品类配置，合并重复提醒，设置负责人和跟进结论。 |
| 6 | 活动复盘模板 | 券活动、会员、投放与核销分析 | 统一投放、领取、核销、带动销售、毛利及承担成本；考虑退货和对照期，不把活动期间全部销售直接归因于活动。 |

AI 建议后置于指标和权限稳定之后，优先做“有数据来源的异常解释、带链接的周报草稿、基于角色授权的问数”。金额计算和审批仍由确定性规则与现有业务流程完成。

## 三、实施顺序与验收

建议拆成三个可独立验收的批次，工作量估计需要结合负责人和线上部署情况细化：

1. **先补安全与实时可信性**：业务接口鉴权、上传控制、凭据整改、健康检查、手机同日期刷新。完成后用匿名账号、越权账号和正常账号验收。
2. **再稳住交付与数据**：统一测试入口、发布追溯、备份恢复演练、财务口径标识、数据同步状态、手机按需加载。
3. **最后形成岗位闭环**：从合同临期与租赁应收待办试点，再扩展品牌档案、月结复核及经营异常跟进。用处理完成率、超期事项、人工核对耗时和活跃使用岗位评估价值。
