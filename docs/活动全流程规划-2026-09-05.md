# 活动与卡券营销全流程规划：投放、ERP/CRM关联、AI分析与供应商结算

日期：2026-09-05。本文是待评审的业务与系统规划，不是已实现功能清单。

已确认：活动卡券结算以商场与品牌/供应商分摊结算为主。外部发券平台资金结算暂不作为本轮主流程。

新增范围：全年新人券、专项活动券、阶段性品牌券统一纳入投放管理；设计标准AI经营分析报告。以下为目标方案，不代表接口、指标和AI功能已实现。

本日补充了只读真实数据核查（成功证据主要采集于12:50—12:56，北京时间），结论见第14节。此前各节中“未查询/待核实”描述的是最初规划阶段；是否已核实以第14节限定的样本和范围为准。

## 1. 总体方向

将现有“活动建档与分析”升级为“活动工作台”。一个活动档案贯穿申请、规则确认、ERP执行、CRM投放、交易追踪、效果分析和费用结算。ERP与CRM继续负责各自的正式执行，ShopView负责组织工作、关联证据、预核算、复核和跟踪结果。

补充方向：新活动从ShopView发起并完成方案设计，随后向ERP、CRM交付批准的配置，接收执行回执和业务数据。会员分析与卡券连带分析是活动经营主线；费用结算是财务主线，两者共享活动身份与源交易，分别采用经营和结算口径。历史活动仍支持关联补档。

目标架构采用“统一发起、分系统执行、数据回流”：ShopView管理批准方案及版本；ERP/POS执行商品、促销、收返券与正式结算；CRM管理会员身份、人群执行与投放。具体发券由实际渠道所属系统执行，不假定所有券都由CRM发放。不支持的玩法在发布前阻断或转为明确的人工交付，不能静默丢弃规则。

每个活动打开后应直接回答：

1. 谁发起、谁参与、活动现在进行到哪一步？
2. ERP规则和CRM投放是否已完成、是否与确认方案一致？
3. 发了哪些券、谁使用、在哪些商品上使用、带来多少销售？
4. 哪些费用由商场承担，哪些由供应商承担，计算依据是什么？
5. 费用是否已经计入其他结算渠道，最终落在哪张结算单，是否存在后续退货调整？

## 2. 当前为什么没有串起来

本次核对了活动页面、活动建档/报表服务、规则ODS服务、凭证匹配和月结代码、ERP结算接口，以及仓库内的ERP存储过程资料。没有查询生产CRM配置或验证线上ERP结算结果。

| 环节 | 当前代码可见的能力 | 衔接缺口 |
| --- | --- | --- |
| 活动建档 | `coupon_campaigns`记录门店、档期、券种、ERP编号与说明 | 券种是字母列表，缺少逐券方案、CRM任务/批次、承担规则与完整状态流转 |
| ERP关联 | 从已校验ODS读取已审核收券规则摘要，保存规则快照 | ERP编号和摘要不足以表示费用承担规则、实际执行版本和逐笔命中结果 |
| CRM关联 | 分析从券日志识别发放及来源 | 当前主档没有明确CRM券模板/投放任务/批次映射；不能据日志推断目标人群、限领或投放完成状态 |
| 活动分析 | 按首次发券资产归属，分析核销、小票、退货、会员、品牌和增长试算 | 尚未形成供应商/合同粒度的结算费用证据链；经营分配口径不能直接当成供应商费用 |
| 财务卡券管理 | 凭证匹配、收入占比、每日变动、月结草稿和确认 | 主要按门店、券种、日期/月份组织，与活动主档及供应商承担之间缺少明细桥接 |
| ERP供应商结算 | 已能查询结算单、付款单和费用明细 | 缺少活动费用行与ERP实际扣费行的对应、差异和重复计费检查 |

两个具体限制尤其重要：

- 现有活动分析只纳入活动日期内的核销与销售退货。活动后的退货不进入当前报告口径，因此它不能原样承担全生命周期结算。
- 当前页面的ERP规则等页签放在报告加载成功之后。截图中“正在关联……”时，用户缺少独立查看准备进度和处理事项的入口。

## 3. 统一业务身份：活动、券方案、批次、交易、费用

本节原有活动链适用于专项活动；结合全年新人券和阶段品牌券，统一模型扩展为“投放计划 → 券方案版本 → 执行任务/发放批次 → 券资产与流水”。活动档案作为专项活动的业务上下文，保留既有ID与报表，不把全年计划硬塞成一档超长活动。具体规则见第11节。

推荐的数据主线：

```text
活动主档
 ├─参与明细：部门 / 柜组 / 品牌 / 供应商 / 合同
 ├─券方案及版本
 │   ├─ERP收券/返券/买券规则与审核记录
 │   ├─CRM券模板 / 投放任务 / 发放批次
 │   └─费用承担协议与ERP分摊规则
 └─券资产及生命周期流水
     └─核销/退货小票 → 商品行 → 交易时点供应商与合同
         ├─经营分析与活动复盘
         └─费用明细 → 复核/对账 → ERP结算行 → 后续调整
```

实施原则：

- 专项活动沿用现有 `coupon_campaigns.id`，不另建一套互不关联的活动主档；新增投放计划与已有活动显式关联。活动编码作为业务显示编号。
- 一个活动允许有多份券方案、多组ERP规则、多次CRM投放。先保留单店活动，未来多店联动可以增加上层活动组，避免先破坏现有门店权限。
- B/E/H/M这类券字母是源系统券种属性，不是活动或投放批次的唯一身份。同字母、同时间可能存在不同用途。
- 归属优先使用明确的源系统ID、投放批次和资产关系；日期、名称、金额仅作为候选匹配条件。无法确认的进入待归属池。
- 若一个底层余额资产可能被多次充值，需先核实资产粒度；必要时在资产下增加发放批次/充值层。不能默认“同一资产永远只有一次发放”。
- 已确认的归属不随之后的核销日期、转赠或退货日期自动改变。纠错应有版本、审批和受影响结果清单。

## 4. 活动工作台怎么设计

活动列表用于筛选与进入档案；进入一个活动后，固定显示活动编码、门店、负责人、阶段、未解决事项及数据截止时间。

工作台建议分七个页面：

| 页面 | 主要内容 | 主要操作 |
| --- | --- | --- |
| 总览与待办 | 生命周期进度、各系统准备情况、关键业务/费用摘要 | 跳到待处理事项、查看责任人和处理记录 |
| 方案与参与范围 | 基础信息、各部门申报、参与/排除商品、附件 | 填报、汇总、退回、确认方案版本 |
| 券方案与系统关联 | 每种券的发放、使用、有效期，ERP和CRM关联 | 关联源单据、导出配置清单、回读核验、确认差异 |
| 交易与异常 | 发放、领取、核销、退券、冲正、延期、转移等流水 | 查小票/商品行、确认归属、分配异常处理人 |
| 效果分析 | 券种、会员、品牌、销售、毛利、增长试算 | 选分析口径、钻取、生成带版本的复盘报告 |
| 费用分摊与结算 | 供应商/合同承担、商场承担、已扣/待扣/差异 | 生成草稿、复核、对账、交付ERP、核验结果 |
| 档案与变更 | 方案、规则、费率、审批、结算和调整版本 | 查看来源、版本差异、关联单据与操作记录 |

卡券月结、凭证匹配、联营结算单保留专业入口，但从活动工作台进入时自动携带活动、券方案和相关源行范围，返回时保持上下文。没有精确活动归属的旧汇总行显示为“未分配”，不伪装成按活动过滤成功。

工作台外壳、主档和准备进度先加载；ERP、CRM、分析、结算分别加载并显示各自更新时间。大报告失败不妨碍查看活动配置或继续处理异常。

### 4.1 效果分析的完整结构

效果分析作为一级经营入口，下设“经营总览、会员分析、卡券转化、连带分析、品牌商品、增量评估”。复用当前已有会员分层、会员明细、券种汇总、关联小票、连带品牌和增长试算，不另建脱节报表。

| 分析主题 | 活动前要设置 | 活动中/后回答的问题 |
| --- | --- | --- |
| 会员分析 | 拉新/召回/促活/升单等目标；目标人群定义及快照；会员分层时点；观察窗口 | 哪类会员收到、领到、使用了券？新客首次购买、沉睡客回流如何？活动后是否再次购买？ |
| 卡券转化 | 每种券目的、渠道、目标人群、发放/领取机制、有效期 | 成功发放、领取、使用、余额及失效表现；不同券方案和渠道的差异 |
| 连带分析 | 同票连带、后续购买、跨品牌流转分别定义；商品分配证据 | 用券小票净销售、另付金额、件数/客单、毛利；是否带动其他品牌或品类消费？ |
| 品牌商品 | 冻结参与范围和可用基准 | 哪些品牌受益、哪些仅承担费用？参与商品与其他商品的销售、毛利有何变化？ |
| 增量评估 | 基准期、对照范围、重叠活动处理及估算方法 | 观察到的增长有多少可能来自活动？证据是否足以支持因果结论？ |

### 4.2 指标与归属口径

每档活动选1—3个主指标，不要求所有活动使用相同目标。例如拉新活动主看“活动新客首购人数”和“新客后续复购率”，销售型活动主看“净连带销售”，召回型活动主看“目标沉睡会员购买转化率”。阈值根据历史基准、预算和人群规模另行确认，不先填通用目标。

- 新客须区分新注册会员与历史从未购买会员；沉睡会员的回看周期在方案中明确。会员等级采用活动前快照用于分组，活动后升级另列，避免分组随当前等级漂移。
- 使用转化率按同一活动、同一发放队列的去重使用人数/成功获券人数计算，区分曾使用与退货后净有效使用；有独立领取环节时另看领取转化。人次、人数、券资产数、券面张数和金额不混用；无领取事件不补造漏斗。
- 后续复购按约定锚点（例如首次有效用券日）后30/60日分别观察；仅完整走完窗口的队列进入成熟复购率分母，并显示未成熟人数。天数是可选分析窗口，不是当前已支持能力。
- 核销券关联小票净销售，与会员本人全部净销售分别展示。持券人、实际小票会员、发券会员不一致时保留关系及未知项，不强行归为同一人。
- 同票多券、多人持券、跨活动叠加时，先按小票去重；活动间共享归因明确标注不可直接相加。需要汇总成可加总归因销售时，使用版本化的分配规则并保证不超过原小票净销售。
- 跨品牌连带区分发券来源品牌与用券商品品牌，按源证据建立流向；CRM定向赠券无来源品牌时显示“CRM投放”。券在某品牌可用不代表该品牌实际承接了销售。
- 另付金额取可核验付款组成，区分现金、银行卡、储值等方式，不能默认用“销售额减券面额”当作现金收入。品牌/商品的券分配缺失时标记未知，不平均摊平。
- 当前“前4周同星期+同部门非参与柜组校准”的增长试算继续标为估算。无有效对照不能称真实增量；若要实验评估，在活动开始前设计可比对照与合法的人群分组。
- 守护指标至少包括预算消耗及退货/冲正情况；同时显示归属缺失、源数据截止时间。活动成本和利润口径需核验是否已在净销售或毛利中扣除，避免重复减费。

各分析卡片保留定义、分母、观察期、来源、更新时间和可钻取明细。执行期由企划/CRM岗监控转化并处理投放异常，档期结束生成经营复盘，观察窗到期补充留存复盘，财务确认后补充实际费用；这些报告各自保留版本。

## 5. 六个阶段及岗位职责

| 阶段 | 主责 | 必须形成的结果 | 进入下一步的条件 |
| --- | --- | --- | --- |
| ①活动申请 | 企划发起，品类主管填报 | 活动目标、参与品牌/商品、券方案、费用协议、负责人 | 必要信息完整；各部门提交完毕或明确不参与 |
| ②规则确认 | 营运汇总，财务确认承担/折算口径 | 批准的方案版本、ERP/CRM配置清单 | 参与范围、时间、限领/限用、费用基数及承担方明确 |
| ③系统准备 | ERP操作岗、CRM操作岗 | ERP审核结果、CRM任务/批次、发布前核对单 | 必需系统已就绪，关键差异处理完成 |
| ④活动执行 | 企划监控，品类主管跟进 | 实际发放/核销、异常处理、规则变更记录 | 经营档期结束后进入复盘；券生命周期继续跟踪 |
| ⑤费用预结算与复核 | 系统生成草稿，品类主管/供应商核对，财务复核 | 按供应商、合同、费用项目的确认明细 | 归属、基数、费率、原单与重复计费问题已处理 |
| ⑥ERP结算与归档 | ERP结算岗、财务 | ERP单据及明细回读、确认版本、未结事项 | 确认费用与ERP实际入单匹配；剩余事项明确挂起或进入后续调整 |

供应商参与的具体确认方式可以沿用现有对账流程；没有供应商系统访问能力时，先导出对账单并保存回执。

活动经营状态与费用结算状态分开：

- 活动：草稿 → 待确认 → 待上线 → 进行中 → 档期结束 → 归档，支持退回/取消分支。
- 券：待发放/发放中/仍可使用/有效期结束等，由方案与实际流水共同决定。
- 结算批次：草稿 → 待复核 → 有争议/已确认 → 待入ERP → 已入单待核验 → 已结算。
- 后续退货形成关联原结算的调整单；活动档期结束不代表券全部失效，也不代表费用已结清。

取消活动不能默认撤销已经发出的券；停发、停用、退券分别以ERP/CRM实际执行回执为准。

## 6. ERP和CRM怎么关联

### ERP：从“编号备注”升级为可核验的规则清单

每条关联记录源系统、门店、档期、规则种类、单据号、审核状态、生效区间、业务版本、源更新时间和同步批次。

规则至少区分：发券/返券、收券、买券、费用分摊。依赖关系依据活动玩法确定，不要求每个活动具备所有规则。

重要代码证据：仓库 `建表/gpp/Ticketmana.txt` 的 `Bapprove_Ft_Sq` 在审核费用分摊定义时写入 `Tktgoodsfqft`，注释区分“按销售额、按返券额、按收券额”，并保存供应商承担比例。现有活动规则ODS服务主要读取 `TKTGOODSYQRATE` 收券规则摘要，两者用途不同。

因此需要核验分摊规则及实际分摊结果的来源。`Tktgoodsfqft`、`tktsellfqamt`、付款商品分配数据和ERP费用明细是候选证据，不因表名相似就认定为最终结算依据；尤其不能把返券分配与收券费用分摊混为一谈。应以正常销售、部分退货、跨品牌小票等样本核对ERP结果后再定口径。

第一阶段建议继续“ShopView确认方案 → 导出ERP录入/导入清单 → ERP审核 → 回读对比”。后续确认正式接口后再支持创建ERP草稿，保留ERP正式审核。

### CRM：从“识别发券日志”升级为明确的投放任务关联

每个券方案可关联多个CRM任务，保存：模板ID、活动/任务ID、发放批次ID、渠道、目标人群版本、发放时间、有效期、计划数量、限领规则、实际成功/失败数及回执。

区分计划投放、实际发放成功、会员领取、券资产生成和后续核销。不同CRM渠道未必存在独立“领取”事件；缺字段时显示“源系统未提供”，不能把计划数直接当作领券数。

需要补做一次CRM数据字典与只读样本核验，明确任务/批次如何关联到实际券资产；现有日志来源码只能说明来源类别，不能证明完整CRM配置已经接通。

支持关联现有CRM任务和导入任务回执。只有确认接口、权限及幂等机制后，才评估从ShopView直接发起投放。重复点击和超时重试不得重复发券；来源状态未知时先查询原任务，不能盲目重发。

### 统一发起的发布机制

活动创建向导建议为“目标与人群 → 品牌商品 → 券玩法 → 承担预算 → 分析计划 → 预检审批”。分析计划包括主指标、基准及观察窗口，因此会员、连带、结算从创建时就关联同一版本。

批准版本生成分别面向ERP和CRM的发布任务，记录活动ID、方案版本、源系统单据ID、状态和回执。两边不具备跨系统原子事务，必须分开显示待提交、处理中、成功、失败和状态未知；ERP成功而CRM失败不显示整体上线。明确依赖顺序，例如需要ERP先可用的券，核验ERP生效后才允许发放。

自动接口接通前仍从ShopView设计和审批，通过配置清单/导入模板交付执行，再回读核验。自动化后先创建源系统草稿并保留审核，使用业务幂等键防重复；未知结果先查状态。变更产生新版本与差异预览，评估已发券影响；撤销活动不自动撤销已执行任务。

方案取舍：仅关联现有ERP/CRM档案适合历史补档；“ShopView统一发起、ERP/CRM执行”是新活动推荐主流程；在ShopView重做POS促销和CRM会员引擎会扩大兼容及资金风险，不纳入本次建设。

## 7. 费用结算如何做到可追溯

### 7.1 将三类金额分别管理

| 金额 | 回答的问题 | 来源/依据 |
| --- | --- | --- |
| 券面额及实际核销额 | 发出和使用了多少券？ | 券资产、流水及付款核对 |
| 经营效果金额 | 关联销售、毛利和估算增长是多少？ | 小票与商品行，明确去重和分析分配口径 |
| 结算费用金额 | 哪个供应商实际应承担多少、还需入账多少？ | 经确认费用协议、执行规则、交易明细与已入账证据 |

收入折算比例与供应商承担比例分别命名、版本化；两者不能互相替代。连带销售也不能直接当作增量销售，按核销金额分配的小票销售不能直接当作供应商扣费基数。

### 7.2 承担规则必须前置到活动确认

每条规则至少明确：适用门店/品牌/柜组/商品、供应商、合同、计算基数、费率及其单位、含税口径、最低/最高承担、排除范围、叠加方式、生效时间、退款处理、结算方式、确认人和协议附件。

规则按协议支持销售额、返券额、收券额或固定金额等模式。具体公式从ERP样本和协议确认，不能先假定所有活动都按净核销额结算。

优惠发生地、券发行地、受益品牌与费用承担方分别保留。A品牌销售产生的券在B品牌使用，不代表必然由B品牌承担；须由已确认规则决定。合同归属按交易/协议适用时点确认，不能用当前合同覆盖历史关系。

### 7.3 结算最小明细

每条费用至少能追溯：

`活动 → 券方案版本 → 发放批次/资产 → 业务流水 → 原小票与商品行 → 供应商/合同 → 费用规则版本 → 草稿费用行 → ERP入单行`

ERP返回实际分摊结果且字段已核验时，优先引用结果并保留来源；暂时缺少结果时，依据已确认规则计算预估。预估、待复核、已确认、已入单在页面上明显区分。

跨品牌小票优先使用可核验的商品行分配证据；没有明细时不能默认平均分摊。辅助试算必须标为预估，等待确认后才能进入正式费用。

### 7.4 防止重复扣费

每条费用行记录结算路径：已通过票减/销售扣率体现、已由ERP自动生成费用、拟另行扣费、仅商场承担等。

同一活动费用不能既通过销售净额/扣率承担，又额外生成费用单。核对必须落到“同一来源费用组件”，不能仅凭金额相等或名称相似认定已扣。

供应商对账单建议显示：活动、合同、费用项目、计算基数、协议费率、应承担、已在既有渠道体现、待新增扣费、退货调整、差异和ERP单据号。平台已入单不等于款项已支付，结算状态与付款状态分开。

### 7.5 退货和跨期调整

同时保存活动归属、业务发生日、结算期间：

- 未确认草稿：纳入新到退货后生成新版本，显示差异。
- 已确认未入ERP：依据流程撤回或补充调整，不能悄悄覆盖已确认金额。
- 已入ERP/已结算：追加正负调整单，关联原活动、原费用行与原ERP行，在允许的后续期间处理。
- 缺原单、缺费率、缺合同、归属冲突、可能重复扣费：挂起受影响明细；不把缺失值当成0。
- 不受影响的确认明细可以形成部分结算批次，同时展示挂起金额和剩余事项；活动不能因此显示“全部结清”。

活动经营分析保留“档期内表现”；另外提供“截至某日的全生命周期表现”。二者都说明退货范围，历史已导出版本保留，不在后台静默改写。

## 8. 数据与权限规划

建议在现有表和服务上增量扩展，以下是概念对象，不是立即执行的建表SQL：

| 对象 | 关键作用 |
| --- | --- |
| 活动主档及参与明细 | 沿用现有活动ID，增加责任人、状态、参与范围和审批 |
| 券方案版本 | 把券字母、有效期、发放/使用规则与费率确认分开管理 |
| 外部系统关联 | 一对多记录ERP单据、CRM任务/批次及核验状态 |
| 人群与分析计划版本 | 目标人群、活动前分层、主指标、基准、观察窗口；后续结果可追溯 |
| 发布任务与执行回执 | 按系统记录批准版本、幂等键、失败/未知状态、重试及差异 |
| 资产归属与事件关系 | 记录资产/发放层归属、证据、确认方式，关联退货与原单 |
| 承担规则版本 | 保存供应商/合同、基数、费率、时效及审批证据 |
| 活动费用明细 | 存放实际/预估来源、原始金额、分担、已体现路径和异常 |
| 结算批次与ERP行关联 | 支持分批结算、一张ERP单含多活动、一活动进入多张单据 |
| 变更/调整与复核记录 | 保留历史版本、纠错原因及关闭依据 |

统一保存来源系统、源业务主键、数据更新时间和同步批次。不同数据源分别显示新鲜度；重复同步按源唯一键去重，规则历史有生效时间，不能把今天采集的规则快照称为活动当时实际执行版本。

确认后的结算版本冻结来源范围和截止点；数据晚到进入差异清单，不自动覆盖。金额用Decimal、统一分位精度，尾差有确定且可解释的归集方式。

权限在后端按操作和范围共同校验：企划维护主档、品类主管维护本部门参与明细、营运确认配置、CRM岗维护投放回执、财务确认费用/结算。供应商只看自己的结算单及必要商品明细，会员身份信息脱敏。更改费率、归属与确认结算分别授权；关键变更保留操作人，按业务制度设置复核人。

现有活动报表只允许整店数据范围，第一期可继续使用这一限制。若开放给品类主管，必须先落实后端部门范围过滤及导出限制，不能只隐藏其他部门菜单。

## 9. 用七夕四券活动做试点

建议以截图中的“中心七夕四券活动”作为历史对照样本；活动ID、源单据和实际结算状态在实施时重新读取核实。

1. 保留原活动主档，拆出B/E/H/M四份券方案，补齐名称、发放渠道、规则版本与实际有效期。
2. 将ERP档期2205关联到审核单据，同时找出费用分摊规则及实际执行结果；缺失部分明确列待补。
3. 逐券关联CRM模板、任务和批次；无CRM任务来源的券明确标注POS返券、手工充值等路径。
4. 选三到五个品牌/供应商，取得既有承担协议和真实ERP结算样本。
5. 覆盖正常核销、同票多券/跨品牌、部分退货、档期后退货、既有票减或自动费用五类案例。
6. 先生成只读对账结果，比较ShopView预核算与ERP实际结果；逐笔解释差异后，再确定正式生成费用的范围。
7. 同步复核现有会员分层、会员明细、四券转化、关联小票及连带品牌，核对同票多券不重算。缺活动前人群快照时明确不可回溯，不用当前画像冒充历史。
8. 七夕历史样本用于分析和结算回归；另选下一档新活动试跑“系统内创建→审批→ERP/CRM交付→回执”，先采用草稿或人工交付，不对历史活动重新发券。

这样可以先回答“费用到底怎么算、ERP已经扣了多少”，再决定哪些动作适合自动化。

## 10. 分期建设与验收

| 批次 | 范围 | 验收结果 |
| --- | --- | --- |
| 第一批：统一发起与分析入口 | 三类投放计划、创建向导、人群/目标/分析计划、逐券方案、ERP/CRM交付任务、待办、分区加载；完整保留会员及连带分析入口 | 新人券、专项活动券、阶段品牌券均可建档；下一档活动在ShopView起草审批，源系统执行状态可核验；现有分析回归通过 |
| 第二批：经营与费用双线贯通 | 会员队列/后续复购、逐券转化、跨品牌连带、标准AI报告草稿；七夕样本、承担规则、只读预核算、防重复检查 | 会员/小票明细与汇总可核对；AI数字可追溯，缺数据不下确定结论；观察窗未成熟有提示；每条供应商费用可追溯并定位ERP差异 |
| 第三批：把结算做成闭环 | 复核、供应商对账、结算版本、ERP模板交付、回读匹配、退货调整 | 已确认费用能跟到ERP行；重试不重复扣费；跨期退货有可审计调整单 |
| 第四批：减少跨系统操作 | ERP/CRM接口草稿或投放联动、任务状态回执、后台报告生成 | 仅在接口、授权与样本验收齐备后启用自动执行；保留人工处理路径 |

三个尚需在实施前核实的事实，不阻碍当前总体规划：

1. CRM正式模板、任务、批次ID与券资产的关联字段，以及可用的查询/导入/API能力。
2. 各活动费用由销售额、返券额还是收券额计算，承担方和合同如何确定；ERP实际费用结果落在哪些源行。
3. 费用哪些已通过扣率/票减体现，哪些要新增扣费；供应商确认、财务复核与后续调整的现行业务要求。

现阶段不建议直接重做ERP/POS促销计算，也不建议直接把当前活动分析金额写进供应商结算单。优先交付第一批和第二批的试点结果，形成可供业务、营运、CRM及财务共同验收的方案。

## 11. 多类型卡券投放管理

### 11.1 三种业务模板，共用执行和数据底座

| 业务模板 | 管理方式 | 主要评价方向 | 复盘节奏建议 |
| --- | --- | --- | --- |
| 全年新人券 | 年度/长期计划，规则版本与实际发放任务独立记录；持续按注册/获券队列观察 | 新客获券后首购转化、成熟队列复购；获券人数和成本作为驱动/约束 | 运营周看，正式月报；不等待全年结束 |
| 专项活动券 | 关联活动档案，一档可含多份券方案、多渠道多批投放 | 按目标选择净连带销售或会员转化，增量试算辅助；预算与退货约束 | 活动中快报、档期复盘、券生命周期/费用补充报告 |
| 阶段品牌券 | 品牌/供应商/合同参与范围加投放阶段；可独立，也可关联大型活动 | 品牌目标人群转化、品牌净关联销售，跨品牌流转辅助；分担费用约束 | 阶段报告及合同约定的结算周期 |

三类是业务模板，不是互斥身份限制。“品牌新人券”可以同时具有新人目标、品牌范围和阶段时效。数据字段分别记录经营目标、持续方式、适用范围、来源渠道，避免后续再增加大量互斥类型。

### 11.2 投放计划、批次与券有效期分开

- 投放计划规定为什么发、发给谁、总体预算与责任人；券方案版本规定面额、门槛、有效期、适用范围、叠加限制及费用承担；实际任务/批次对应源系统执行和成功回执。
- 一年内规则调整产生新版本，已经发出的券保留原版本与权益。停止计划只停止后续发放，不直接将存量券失效。
- 计划期限、发放时间、逐券有效期、分析观察窗、结算期间分别管理。例如年底获券跨年使用，仍归原投放计划/版本，业务发生与财务结算可以跨年。
- 全年按月生成分析队列即可，不必人为新建十二档活动，也不伪造十二个CRM执行批次；源系统有日批、实时触发或任务时保留实际粒度。
- 既有活动归属依赖门店、券种和日期且有重叠限制，不能直接承载长期计划与短期活动并行。扩展前须核验来源任务/批次与资产关系；只有精确归属可用时才调整限制，不能先放开冲突校验。
- 每笔发放/充值事件只有一个确认的投放来源；同一张券可以在不同活动期间消费，另记消费场景关系，不重复计发放及费用。大型活动展示“专项券贡献”和“同期新人/品牌券消费”两组视角，跨场景汇总去重。
- 人群/预算重叠只作为预检提醒；是否可叠加、是否重复获券由批准方案和ERP/CRM执行规则决定。分析标签不能绕过实际交易规则。
- 供应商承担由逐券/费用规则确认。新人券也不默认全部商场承担；品牌券也不默认全部品牌承担。

工作台顶层增加“投放计划、活动档案、券方案、执行监控、经营分析、费用结算、AI报告”入口；仍共享上下文和权限。历史活动入口兼容保留。

## 12. 标准AI分析报告

### 12.1 产品形式

提供“生成分析草稿”，支持单活动、单投放计划/阶段、月度卡券组合报告。报告主体使用统一模板，再按新人券、专项活动券、品牌券选择对应分析段落。首版建议生成待审核草稿与版本化导出；计划任务、自动发送或自动修改投放均需另行配置和授权，本规划不启用这些动作。

跨计划比较只比较口径一致且观察窗可比的数据，展示人群、门槛、有效期和渠道差异，不将新人券与大促券按裸核销率直接排优劣。

### 12.2 固定报告结构

| 章节 | 必须输出 |
| --- | --- |
| 报告封面与口径 | 范围、目的、统计截止点、各源更新时间、观察窗、规则/数据版本、草稿/已审核状态 |
| 管理摘要 | 至多3条关键结论，各附核心数字、比较基准和证据；无依据不强行凑齐 |
| 投放与转化 | 计划与成功发放、获券/核销人数及金额、到期情况；说明分母、缺失环节与样本成熟度 |
| 会员效果 | 新老/沉睡/等级分层、本人消费与持券关联消费、首购与复购；解释人群定义 |
| 连带与品牌商品 | 小票净销售、另付构成、客单/件数、毛利、跨品牌流转；区分观察关联与估算增量 |
| 成本与结算 | 已核验的商场/供应商承担、预估/确认/已入ERP金额、退货调整；缺数据则标未具备结算评价条件 |
| 异常与限制 | 数据缺失、版本变化、叠加活动、退货、观察窗未成熟和小样本；影响到哪些结论 |
| 建议与追踪 | 至多3项优先建议，每项包含证据、待验证假设、责任岗位、预期方向、验证指标与下次复核点 |

每档选1—3个主指标，其余为诊断明细，不把报告变为所有指标平铺。主指标定义继承活动/计划创建时的分析计划；无法测量目标时，报告应明确缺口。

### 12.3 数据先计算和校验，再交给AI解释

链路：冻结报告范围/来源截止点 → 后端计算指标与对照 → 数据质量检查 → 形成带证据ID的数据包 → AI生成结构化分析 → 数字/引用校验 → 人工审核 → 保存报告版本。

数据包至少包含指标ID、定义版本、数值及单位、分子/分母、去重粒度、对照值、时间范围、数据源/证据ID、质量标记与可授权钻取入口。敏感身份不进入默认数据包，使用聚合或脱敏标识；跨系统导出与外部模型接入需遵守既有权限并另核数据处理边界。

- 核心金额、比例、去重和财务分摊由可测试的后端逻辑计算，AI不负责决定结算金额，也不直接生成可执行ERP扣费指令。
- AI输出区分“已验证事实、可能解释、行动建议”。原因缺少证据时用待验证假设，不把观察到的销售上升直接解释为活动带来的增长。
- 无目标人群、无匹配分母、未到观察期或源延迟时，相应指标不输出确定评价。可保留不受影响章节；关键数据不足时返回数据不足报告。
- 每项事实结论必须引用当前数据包中的证据；引用不存在、数字/单位/分母不一致时阻止通过并提示复核。模型失败时仍可查看标准数据报表，不显示空白成功报告。
- 记录数据快照、指标定义、提示模板和模型版本、生成时间及审核人。源数据晚到或退货更新时产生新版，不覆盖已经审核版本。
- 反馈给AI的活动说明、附件、源系统文本仅作为业务数据，不能作为执行指令或覆盖报告规则。AI不得自行改变券门槛、人群、发放数量或费用比例。

### 12.4 首版验收

选一份新人券月度成熟队列、一档七夕活动和一份阶段品牌券各生成报告草稿。历史人群快照缺失时不补造。

### 已确认的关联和必须修正的假设

1. **七夕不用只靠日期猜归属。** CRM模板532623/B、532624/E、532625/H、532626/M，通过`third_cno ↔ tcflvipseq`并限定门店和券种，1,925个资产键与项目库全集一致。应保存模板关联；无需先改写原ERP券日志中为空或0的活动编号。
2. **发放期和使用期必须独立。** 694个资产在8月14日前已发，约36.1%；CRM设置允许8月5日开始发放，8月14日才开始使用。按经营档期截取发放会漏计。
3. **会员历史不是完全缺失。** CRM存在`member_level_track`。七夕828人中782人有活动开始时的有效等级记录；另外44人活动开始后才注册，2名既有会员历史待补。新增同步“券记录mem_id→member.id→member_scenes.id→等级轨迹”链，不能直接拼接两种ID。历史有效期边界还须正式确认。
4. **小票关联可用，会员身份仍要分开。** 711笔消费券流水及63笔退券流水全部唯一关联小票。消费券流水中452笔身份一致、11笔小票未登记会员、248笔身份不同；这些是流水数，不是去重小票数，也不是违规结论。
5. **品牌券按兑现方式分支。** 海蓝之谜VIP悦享券是POS类型（模板532669，ERP券种M），6,425条均能关联CRM侧券日志；GIADA500元专享券是gift（532644），3,917条无ERP券编号，金额字段为空。不能从名字提取500元作为券面金额，更不能把没有ERP编号直接当发券失败。
6. **新人券需要待核发放状态。** 中心新客券（2026）模板529693、ERP券种P，明细14,440条，14,428条可连到CRM侧券日志；12条历史记录缺第三方券编号，原因待查。它们应保留在待核池，而不是直接算成功到账。
7. **费用公式必须重新核准。** 档期2205的`TKTGOODSFQFT`共474条规则，实际类型A/B/C、计算方法5，与旧字段注释1/2/3不同。仓库过程的实际代码也使用A/B/C；不能机械套旧注释。该档期规则不等于四券全部费用，须继续匹配付款方式、券种、商品/供应商、合同及已入ERP的费用行。
8. **AI输入必须用明确指标，不拼现成计数。** E券模板核销计数401、当前`used_status=1`记录377、消费O流水406笔，代表的口径待核；不能任选一个当核销人数。AI先读取后端定义的去重人数、资产及带符号流水，分别解释当前状态和历史事件。
